| Field          | Value                                                                                           |
| -------------- | ----------------------------------------------------------------------------------------------- |
| **Epic**       | 4 — Job Management & Background Processing                                                      |
| **Priority**   | P0                                                                                              |
| **Summary**    | Define job state model: `queued → processing → completed → failed → cancelled`                  |

> **Implementation note:** Stories 4.1, 4.2, 4.3, and 4.4 were delivered together as part of Story 3.1 because the upload endpoint required the job model, store, background task, and progress wiring to be functional as a unit. This document formalizes the state machine design and serves as the reference specification.

---

## 1. Objective

Define a formal state machine for job lifecycle management. Every job transitions through well-defined states with explicit rules about which transitions are valid, who triggers them, and what data is available at each state.

---

## 2. Acceptance Criteria

| #    | Criteria                                                                                           |
| ---- | -------------------------------------------------------------------------------------------------- |
| AC-1 | `JobStatus` enum with 5 states: `queued`, `processing`, `completed`, `failed`, `cancelled`.        |
| AC-2 | `Job` dataclass holds status, progress, timestamps, video path, error, and pipeline result.        |
| AC-3 | `JobProgress` dataclass tracks `phase`, `current`, `total`, `percent`.                             |
| AC-4 | State transitions are documented with valid source → target pairs.                                 |
| AC-5 | Invalid transitions (e.g. `completed → processing`) are not possible through the store API.        |

---

## 3. State Machine

### 3.1 States

```
┌─────────┐     ┌────────────┐     ┌───────────┐
│ QUEUED  │────>│ PROCESSING │────>│ COMPLETED │
└─────────┘     └────────────┘     └───────────┘
    │                │
    │                │
    │                ▼
    │           ┌─────────┐
    │           │ FAILED  │
    │           └─────────┘
    │
    ▼
┌───────────┐
│ CANCELLED │<─── (also reachable from PROCESSING)
└───────────┘
```

### 3.2 State Definitions

| State          | Meaning                                                   | Data available                          |
| -------------- | --------------------------------------------------------- | --------------------------------------- |
| `queued`       | Job accepted, waiting for a worker to pick it up           | `job_id`, `video_path`, `created_at`    |
| `processing`   | Pipeline is running (detection, segmentation, or cropping) | Above + `progress` (phase, %, current)  |
| `completed`    | Pipeline finished successfully, results ready              | Above + `result` (PipelineResult)       |
| `failed`       | Pipeline errored at some phase                             | Above + `error` (message string)        |
| `cancelled`    | User cancelled the job before completion                   | Above only                              |

### 3.3 Valid Transitions

| From           | To             | Triggered by                     |
| -------------- | -------------- | -------------------------------- |
| `queued`       | `processing`   | Background worker picks up job   |
| `queued`       | `cancelled`    | User calls `DELETE /jobs/{id}`   |
| `processing`   | `completed`    | Pipeline finishes successfully   |
| `processing`   | `failed`       | Pipeline raises an exception     |
| `processing`   | `cancelled`    | User calls `DELETE /jobs/{id}`   |

**Terminal states:** `completed`, `failed`, `cancelled` — no further transitions allowed.

### 3.4 Invalid Transitions (explicitly prohibited)

| Transition                      | Why                                                  |
| ------------------------------- | ---------------------------------------------------- |
| `completed` → anything          | Results are final. Create a new job to re-process.   |
| `failed` → `processing` (retry) | Not supported in v1. Create a new job instead.       |
| `cancelled` → anything          | Cancellation is permanent.                           |
| `queued` → `completed`          | Must go through `processing` first.                  |
| `queued` → `failed`             | Failures only happen during processing.              |

## 4. Data Model

### 4.1 `app/models/job.py`

Implemented in Story 3.1. The complete file:

```python
from dataclasses import dataclass, field
from datetime import datetime, timezone
from enum import Enum
from typing import Optional


class JobStatus(str, Enum):
    QUEUED = "queued"
    PROCESSING = "processing"
    COMPLETED = "completed"
    FAILED = "failed"
    CANCELLED = "cancelled"


# Terminal states — no further transitions allowed
TERMINAL_STATES = {JobStatus.COMPLETED, JobStatus.FAILED, JobStatus.CANCELLED}

# Valid transitions: source → set of allowed targets
VALID_TRANSITIONS = {
    JobStatus.QUEUED: {JobStatus.PROCESSING, JobStatus.CANCELLED},
    JobStatus.PROCESSING: {JobStatus.COMPLETED, JobStatus.FAILED, JobStatus.CANCELLED},
    JobStatus.COMPLETED: set(),
    JobStatus.FAILED: set(),
    JobStatus.CANCELLED: set(),
}


@dataclass
class JobProgress:
    """Tracks progress within the current pipeline phase."""
    phase: str = ""
    current: int = 0
    total: int = 0
    percent: float = 0.0


@dataclass
class Job:
    """In-memory representation of a processing job."""
    job_id: str
    status: JobStatus = JobStatus.QUEUED
    video_path: str = ""
    output_dir: str = ""
    created_at: datetime = field(default_factory=lambda: datetime.now(timezone.utc))
    updated_at: datetime = field(default_factory=lambda: datetime.now(timezone.utc))
    progress: JobProgress = field(default_factory=JobProgress)
    error: Optional[str] = None
    result: Optional[object] = None  # PipelineResult once completed


def can_transition(current: JobStatus, target: JobStatus) -> bool:
    """Check if a state transition is valid."""
    return target in VALID_TRANSITIONS.get(current, set())


def is_terminal(status: JobStatus) -> bool:
    """Check if a status is a terminal state."""
    return status in TERMINAL_STATES
```

**Additions over Story 3.1:** `TERMINAL_STATES`, `VALID_TRANSITIONS`, `can_transition()`, `is_terminal()`. These are used by the job store (Story 4.2) and cancel endpoint (Story 4.6) to enforce the state machine.

### 4.2 Updated `app/models/job_store.py`

Add transition validation to `update_status`:

```python
import threading
import logging
from datetime import datetime, timezone
from typing import Optional

from app.models.job import (
    Job, JobStatus, JobProgress, can_transition, is_terminal,
)

logger = logging.getLogger(__name__)


class JobStore:
    """Thread-safe in-memory job store with transition validation."""

    def __init__(self):
        self._jobs: dict[str, Job] = {}
        self._lock = threading.Lock()

    def create(self, job: Job) -> Job:
        with self._lock:
            self._jobs[job.job_id] = job
        return job

    def get(self, job_id: str) -> Optional[Job]:
        with self._lock:
            return self._jobs.get(job_id)

    def update_status(
        self, job_id: str, status: JobStatus, error: str = None,
    ) -> bool:
        """Update job status with transition validation.

        Returns True if the transition succeeded, False if it was invalid
        (e.g. job is already in a terminal state).
        """
        with self._lock:
            job = self._jobs.get(job_id)
            if not job:
                return False

            if not can_transition(job.status, status):
                logger.warning(
                    "Invalid transition for job %s: %s → %s",
                    job_id, job.status.value, status.value,
                )
                return False

            job.status = status
            job.updated_at = datetime.now(timezone.utc)
            if error:
                job.error = error
            return True

    def update_progress(
        self, job_id: str, phase: str, current: int, total: int,
    ):
        with self._lock:
            job = self._jobs.get(job_id)
            if job and not is_terminal(job.status):
                job.progress = JobProgress(
                    phase=phase,
                    current=current,
                    total=total,
                    percent=round((current / total * 100) if total > 0 else 0, 1),
                )
                job.updated_at = datetime.now(timezone.utc)

    def set_result(self, job_id: str, result: object):
        with self._lock:
            job = self._jobs.get(job_id)
            if job:
                job.result = result

    def delete(self, job_id: str) -> bool:
        with self._lock:
            return self._jobs.pop(job_id, None) is not None

    def list_all(self) -> list[Job]:
        with self._lock:
            return list(self._jobs.values())


# Module-level singleton
job_store = JobStore()
```

**Changes from Story 3.1:**
- `update_status()` now validates transitions via `can_transition()` and returns `bool`.
- `update_progress()` skips updates if the job is in a terminal state.
- Added logging for invalid transitions.

## 5. How Progress Maps to the Pipeline

The pipeline (Story 2.4) reports progress via callback. Here's how it maps to `JobProgress`:

| Pipeline callback                          | JobProgress state                                        |
| ------------------------------------------ | -------------------------------------------------------- |
| `on_progress("detection", 8, 3400)`        | `phase="detection", current=8, total=3400, percent=0.2`  |
| `on_progress("detection", 3400, 3400)`     | `phase="detection", current=3400, total=3400, percent=100.0` |
| `on_progress("segmentation", 0, 1)`        | `phase="segmentation", current=0, total=1, percent=0.0`  |
| `on_progress("segmentation", 1, 1)`        | `phase="segmentation", current=1, total=1, percent=100.0`|
| `on_progress("cropping", 0, 5)`            | `phase="cropping", current=0, total=5, percent=0.0`      |
| `on_progress("cropping", 5, 5)`            | `phase="cropping", current=5, total=5, percent=100.0`    |

The status endpoint (Story 4.5) reads `job.progress` and returns it in the API response.

## 6. How to Verify

```python
from app.models.job import JobStatus, can_transition, is_terminal, VALID_TRANSITIONS

# Valid transitions
assert can_transition(JobStatus.QUEUED, JobStatus.PROCESSING) == True
assert can_transition(JobStatus.QUEUED, JobStatus.CANCELLED) == True
assert can_transition(JobStatus.PROCESSING, JobStatus.COMPLETED) == True
assert can_transition(JobStatus.PROCESSING, JobStatus.FAILED) == True
assert can_transition(JobStatus.PROCESSING, JobStatus.CANCELLED) == True

# Invalid transitions
assert can_transition(JobStatus.COMPLETED, JobStatus.PROCESSING) == False
assert can_transition(JobStatus.FAILED, JobStatus.PROCESSING) == False
assert can_transition(JobStatus.CANCELLED, JobStatus.QUEUED) == False
assert can_transition(JobStatus.QUEUED, JobStatus.COMPLETED) == False

# Terminal states
assert is_terminal(JobStatus.COMPLETED) == True
assert is_terminal(JobStatus.FAILED) == True
assert is_terminal(JobStatus.CANCELLED) == True
assert is_terminal(JobStatus.QUEUED) == False
assert is_terminal(JobStatus.PROCESSING) == False

print("All state machine assertions passed!")
```

## 7. Notes

- **No retry from `failed`** in v1. If a job fails, the user creates a new job. Adding retry would require tracking attempt count and resetting progress — deferred to a future version.
- **`cancelled` stops the background task** only if checked. The worker (Story 4.6) will check `is_terminal(job.status)` periodically to exit early. FastAPI's `BackgroundTasks` doesn't support true cancellation, so the worker cooperatively exits.
- **The `result` field** stores the full `PipelineResult` object in memory. For the MVP this is fine. With a DB-backed store, this would be serialized to JSON or stored as a reference to output files on disk.
