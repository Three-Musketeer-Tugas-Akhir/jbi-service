> **Note:** Absorbs Stories 7.2 and 7.3 from the PRD. Story 1.4 already created `docker-compose.yml` with API, worker, Redis services and volume mounts. This story adds the GPU variant and refines the compose file for production use — no need for separate 7.2/7.3 stories.

---

## 1. Objective

Add a GPU-capable Docker image alongside the existing CPU image so the service can run YOLO inference on NVIDIA GPUs inside containers. Specifically:

- Create `Dockerfile.gpu` using an NVIDIA CUDA base image with PyTorch GPU support.
- Update `docker-compose.yml` with Docker Compose profiles (`cpu` and `gpu`) so users pick the deployment mode with a single flag.
- Update the CPU `Dockerfile` with improvements from later stories (structured logging `--no-access-log`, production-ready CMD).
- Keep the build workflow simple: one compose file, two profiles.

## 3. Detailed Implementation

### 3.1 `Dockerfile` — Updated CPU Image

Update the existing `Dockerfile` from Story 1.4 with improvements from later stories:

```dockerfile
# ============================================================
# JBI Detection & Segmentation API — Dockerfile (CPU)
# ============================================================
# For GPU support: docker build -f Dockerfile.gpu .
# ============================================================

# --- Stage 1: Build dependencies ---
FROM python:3.11-slim AS builder

WORKDIR /build

# Install system deps needed for building Python packages
RUN apt-get update && apt-get install -y --no-install-recommends \
    build-essential \
    && rm -rf /var/lib/apt/lists/*

# Copy requirements and install into a virtualenv
COPY requirements.txt .
RUN python -m venv /opt/venv
ENV PATH="/opt/venv/bin:$PATH"
RUN pip install --no-cache-dir --upgrade pip \
    && pip install --no-cache-dir -r requirements.txt


# --- Stage 2: Runtime ---
FROM python:3.11-slim AS runtime

WORKDIR /app

# Install runtime system dependencies
RUN apt-get update && apt-get install -y --no-install-recommends \
    ffmpeg \
    libgl1 \
    libglib2.0-0 \
    && rm -rf /var/lib/apt/lists/*

# Copy virtualenv from builder
COPY --from=builder /opt/venv /opt/venv
ENV PATH="/opt/venv/bin:$PATH"

# Copy application code
COPY app/ ./app/

# Create storage directories
RUN mkdir -p storage/uploads storage/outputs model_weights

# Expose port
EXPOSE 8000

# Health check
HEALTHCHECK --interval=30s --timeout=5s --start-period=10s --retries=3 \
    CMD python -c "import urllib.request; urllib.request.urlopen('http://localhost:8000/api/v1/health')" || exit 1

# Start uvicorn — no-access-log because Story 6.4 handles request logging
CMD ["uvicorn", "app.main:app", "--host", "0.0.0.0", "--port", "8000", "--no-access-log"]
```

**Changes from Story 1.4:**
- Added `--no-access-log` to uvicorn CMD (Story 6.4 structured logging replaces uvicorn's default access log).

### 3.2 `Dockerfile.gpu` — NVIDIA CUDA Image

```dockerfile
# ============================================================
# JBI Detection & Segmentation API — Dockerfile.gpu (CUDA)
# ============================================================
# Requires: NVIDIA Container Toolkit on the host
# Build:    docker build -f Dockerfile.gpu -t jbi-api:gpu .
# Run:      docker run --gpus all -p 8000:8000 jbi-api:gpu
# ============================================================

# --- Stage 1: Build dependencies ---
FROM nvidia/cuda:12.6.3-runtime-ubuntu22.04 AS builder

# Install Python 3.11 (not included in nvidia/cuda image)
RUN apt-get update && apt-get install -y --no-install-recommends \
    python3.11 \
    python3.11-venv \
    python3.11-dev \
    python3-pip \
    build-essential \
    && rm -rf /var/lib/apt/lists/*

# Make python3.11 the default python
RUN update-alternatives --install /usr/bin/python python /usr/bin/python3.11 1 \
    && update-alternatives --install /usr/bin/python3 python3 /usr/bin/python3.11 1

WORKDIR /build

# Create virtualenv
RUN python -m venv /opt/venv
ENV PATH="/opt/venv/bin:$PATH"
RUN pip install --no-cache-dir --upgrade pip

# Install PyTorch with CUDA first (from separate requirements file)
COPY requirements-torch-gpu.txt .
RUN pip install --no-cache-dir -r requirements-torch-gpu.txt

# Install remaining dependencies (skip torch/torchvision — already installed with CUDA)
COPY requirements.txt .
RUN pip install --no-cache-dir -r requirements.txt


# --- Stage 2: Runtime ---
FROM nvidia/cuda:12.6.3-runtime-ubuntu22.04 AS runtime

WORKDIR /app

# Install Python 3.11 + runtime system dependencies
RUN apt-get update && apt-get install -y --no-install-recommends \
    python3.11 \
    python3.11-venv \
    ffmpeg \
    libgl1 \
    libglib2.0-0 \
    && rm -rf /var/lib/apt/lists/*

RUN update-alternatives --install /usr/bin/python python /usr/bin/python3.11 1 \
    && update-alternatives --install /usr/bin/python3 python3 /usr/bin/python3.11 1

# Copy virtualenv from builder
COPY --from=builder /opt/venv /opt/venv
ENV PATH="/opt/venv/bin:$PATH"

# NVIDIA environment variables (ensures CUDA libraries are visible)
ENV NVIDIA_VISIBLE_DEVICES=all
ENV NVIDIA_DRIVER_CAPABILITIES=compute,utility

# Copy application code
COPY app/ ./app/

# Create storage directories
RUN mkdir -p storage/uploads storage/outputs model_weights

# Expose port
EXPOSE 8000

# Health check
HEALTHCHECK --interval=30s --timeout=5s --start-period=30s --retries=3 \
    CMD python -c "import urllib.request; urllib.request.urlopen('http://localhost:8000/api/v1/health')" || exit 1

# Start uvicorn — no-access-log because Story 6.4 handles request logging
CMD ["uvicorn", "app.main:app", "--host", "0.0.0.0", "--port", "8000", "--no-access-log"]
```

**Key differences from CPU Dockerfile:**

| Aspect                  | CPU (`Dockerfile`)                | GPU (`Dockerfile.gpu`)                                |
| ----------------------- | --------------------------------- | ----------------------------------------------------- |
| Base image              | `python:3.11-slim` (~150 MB)      | `nvidia/cuda:12.6.3-runtime-ubuntu22.04` (~1.5 GB)   |
| Python                  | Pre-installed                     | Manually installed via `apt-get`                      |
| PyTorch                 | CPU-only (from `requirements.txt`) | CUDA-enabled (from `requirements-torch-gpu.txt`)     |
| NVIDIA env vars         | Not needed                        | `NVIDIA_VISIBLE_DEVICES`, `NVIDIA_DRIVER_CAPABILITIES` |
| HEALTHCHECK start-period | 10s (fast startup)               | 30s (CUDA initialization takes longer)                |
| Final image size        | ~2 GB                             | ~6 GB (CUDA runtime + GPU PyTorch)                    |

### 3.3 `docker-compose.yml` — Updated with Profiles

Replace the existing `docker-compose.yml`:

```yaml
# ============================================================
# JBI Detection & Segmentation API — Docker Compose
# ============================================================
# Usage:
#   CPU mode:  docker compose --profile cpu up --build
#   GPU mode:  docker compose --profile gpu up --build
# ============================================================

services:
  # ── CPU API Service ──────────────────────────────────────
  api:
    build:
      context: .
      dockerfile: Dockerfile
    profiles: ["cpu"]
    ports:
      - "8000:8000"
    env_file:
      - .env
    volumes:
      - ./model_weights:/app/model_weights:ro
      - uploads_data:/app/storage/uploads
      - outputs_data:/app/storage/outputs
    depends_on:
      redis:
        condition: service_healthy
    restart: unless-stopped

  # ── GPU API Service ──────────────────────────────────────
  api-gpu:
    build:
      context: .
      dockerfile: Dockerfile.gpu
    profiles: ["gpu"]
    ports:
      - "8000:8000"
    env_file:
      - .env
    volumes:
      - ./model_weights:/app/model_weights:ro
      - uploads_data:/app/storage/uploads
      - outputs_data:/app/storage/outputs
    deploy:
      resources:
        reservations:
          devices:
            - driver: nvidia
              count: 1
              capabilities: [gpu]
    depends_on:
      redis:
        condition: service_healthy
    restart: unless-stopped

  # ── Redis ────────────────────────────────────────────────
  redis:
    image: redis:7-alpine
    ports:
      - "6379:6379"
    healthcheck:
      test: ["CMD", "redis-cli", "ping"]
      interval: 10s
      timeout: 3s
      retries: 5
    restart: unless-stopped

volumes:
  uploads_data:
  outputs_data:
```

**Changes from Story 1.4:**

1. **Profiles added:** `api` runs under `cpu` profile, `api-gpu` runs under `gpu` profile. Only one starts at a time.
2. **`api-gpu` service:** Uses `Dockerfile.gpu`, includes `deploy.resources.reservations.devices` for GPU passthrough.
3. **Worker service removed:** The MVP uses `BackgroundTasks` (tasks run inside the API process). The placeholder worker that ran `sleep infinity` added confusion. When Celery is adopted, a `worker` service will be added back.
4. **Redis has no profile:** It starts in both CPU and GPU modes — always available.

## 4. How to Verify

### 4.1 Build CPU image

```bash
docker build -t jbi-api:cpu .
# Should complete without errors
# Image size: ~2 GB
```

### 4.2 Build GPU image

```bash
docker build -f Dockerfile.gpu -t jbi-api:gpu .
# Should complete without errors
# Image size: ~6 GB
```

### 4.3 Run with CPU profile

```bash
# Make sure .env exists
cp .env.example .env

docker compose --profile cpu up --build

# Expected: api + redis start
# curl http://localhost:8000/api/v1/health
# {"status":"unhealthy","model_loaded":false,...}
# (unhealthy because model not yet loaded — expected on fresh start)
```

### 4.4 Run with GPU profile

```bash
# Requires NVIDIA Container Toolkit installed on host
docker compose --profile gpu up --build

# Expected: api-gpu + redis start
# curl http://localhost:8000/api/v1/health
# {"status":"healthy","model_loaded":false,"gpu_available":true,"gpu_name":"NVIDIA GeForce RTX 3060",...}
```

### 4.5 Verify GPU access inside container

```bash
docker compose --profile gpu exec api-gpu python -c "import torch; print(torch.cuda.is_available(), torch.cuda.get_device_name(0))"
# Expected: True NVIDIA GeForce RTX 3060
```

### 4.6 Verify no duplicate access logs

```bash
docker compose --profile cpu up --build
curl http://localhost:8000/api/v1/health

# Server output should show ONLY structured JSON logs from Story 6.4:
# {"timestamp":"...","level":"INFO","logger":"app.requests","message":"GET /api/v1/health → 200 (1.5ms)","request_id":"a3f8b2c1"}
#
# Should NOT show uvicorn default access log like:
# INFO:     127.0.0.1:12345 - "GET /api/v1/health HTTP/1.1" 200
```

### 4.7 Verify profiles are mutually exclusive

```bash
# Only cpu profile — api-gpu should NOT start
docker compose --profile cpu up -d
docker compose ps
# Expected: api, redis (no api-gpu)

docker compose --profile cpu down

# Only gpu profile — api should NOT start
docker compose --profile gpu up -d
docker compose ps
# Expected: api-gpu, redis (no api)

docker compose --profile gpu down
```

### 4.8 Teardown

```bash
docker compose --profile cpu down
# or
docker compose --profile gpu down

# Remove volumes too:
docker compose --profile cpu down -v
```

## 5. NVIDIA Container Toolkit Prerequisites

For the GPU profile to work, the host machine needs:

1. **NVIDIA GPU driver** installed (version >= 535 for CUDA 12.6).
2. **NVIDIA Container Toolkit** installed.

```bash
# Ubuntu — install NVIDIA Container Toolkit
curl -fsSL https://nvidia.github.io/libnvidia-container/gpgkey | sudo gpg --dearmor -o /usr/share/keyrings/nvidia-container-toolkit-keyring.gpg
curl -s -L https://nvidia.github.io/libnvidia-container/stable/deb/nvidia-container-toolkit.list | \
    sed 's#deb https://#deb [signed-by=/usr/share/keyrings/nvidia-container-toolkit-keyring.gpg] https://#g' | \
    sudo tee /etc/apt/sources.list.d/nvidia-container-toolkit.list
sudo apt-get update
sudo apt-get install -y nvidia-container-toolkit
sudo nvidia-ctk runtime configure --runtime=docker
sudo systemctl restart docker

# Verify
docker run --rm --gpus all nvidia/cuda:12.6.3-base-ubuntu22.04 nvidia-smi
```

For **Windows with WSL2**, Docker Desktop must have "Use WSL 2 based engine" enabled and the NVIDIA GPU driver for WSL must be installed (comes with modern NVIDIA drivers).

## 6. Design Decisions

| Decision                                        | Rationale                                                                                             |
| ----------------------------------------------- | ----------------------------------------------------------------------------------------------------- |
| **Separate `Dockerfile.gpu`, not a build arg**   | A single Dockerfile with `ARG BASE_IMAGE` is tempting, but the Python installation steps differ significantly (pre-installed in `python:3.11-slim` vs manual `apt-get` in `nvidia/cuda`). Two Dockerfiles are clearer and easier to maintain. |
| **Docker Compose profiles, not separate files**  | `docker compose --profile gpu up` is simpler than `docker compose -f docker-compose.yml -f docker-compose.gpu.yml up`. One file, one source of truth. |
| **`nvidia/cuda:12.6.3-runtime`, not `devel`**    | The `runtime` tag (~1.5 GB) includes only CUDA runtime libraries. The `devel` tag (~4 GB) adds compilers and headers we don't need — we're not compiling CUDA code, just running PyTorch. |
| **Python 3.11 manually installed in GPU image**  | The `nvidia/cuda` images are based on Ubuntu, not Python. Installing Python via `apt-get` ensures version consistency with the CPU image. |
| **`start-period=30s` for GPU HEALTHCHECK**       | CUDA initialization (loading driver, allocating context) takes longer than CPU. A 30s grace period prevents false-negative health checks during startup. |
| **Worker service removed**                       | The placeholder `sleep infinity` worker from Story 1.4 served no purpose in the MVP. BackgroundTasks run in-process. Adding a dead service to compose causes confusion ("why is the worker doing nothing?"). It will be re-added when Celery is introduced. |
| **Redis kept without profile**                   | Redis starts in both CPU and GPU modes. Even though the MVP doesn't use it for task queuing, it's lightweight (5 MB Alpine image) and ready for Celery adoption. |
| **`deploy.resources.reservations.devices`**      | This is the Docker Compose v2 way to request GPU access. It replaced the older `runtime: nvidia` syntax. |

## 7. Image Size Comparison

| Image             | Base              | PyTorch      | Final Size |
| ----------------- | ----------------- | ------------ | ---------- |
| `jbi-api:cpu`     | python:3.11-slim  | CPU-only     | ~2 GB      |
| `jbi-api:gpu`     | nvidia/cuda 12.6  | CUDA 12.6    | ~6 GB      |

The GPU image is larger because:
- `nvidia/cuda:12.6.3-runtime` base: ~1.5 GB (CUDA runtime libs)
- PyTorch with CUDA: ~2.5 GB (vs ~800 MB for CPU)
- Python 3.11 installed manually: ~200 MB

This is normal for GPU-accelerated ML containers. Production deployments typically cache the base layers.

## 8. Notes

- **Windows users (WSL2):** Docker Desktop with WSL2 backend supports GPU passthrough natively. No need for NVIDIA Container Toolkit inside WSL — the Windows GPU driver handles it. Just enable "Use WSL 2 based engine" in Docker Desktop settings.
- **`requirements-torch-gpu.txt` was created in Story 1.2.** It contains `torch` and `torchvision` with `--index-url https://download.pytorch.org/whl/cu126` for CUDA 12.6 builds.
- **PyTorch installed twice?** No. In `Dockerfile.gpu`, `requirements-torch-gpu.txt` installs PyTorch with CUDA first. When `requirements.txt` runs next, pip sees that `torch` and `torchvision` are already installed (satisfying the version requirement) and skips them.
- **Story 7.4** will add production vs development configuration (log level, worker count, reload mode) as environment-based overrides.
- **Multi-GPU** is not supported in this setup (`count: 1` in compose). YOLO inference uses a single GPU. Multi-GPU would require model parallelism or running multiple worker containers, which is out of scope for MVP.
