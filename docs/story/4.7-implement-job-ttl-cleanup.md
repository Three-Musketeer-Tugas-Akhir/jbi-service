# Story 4.7 — Implement Job TTL: Auto-Delete Job Data After Expiry

| Field          | Value                                                                                  |
| -------------- | -------------------------------------------------------------------------------------- |
| **Epic**       | 4 — Job Management & Background Processing                                             |
| **Priority**   | P2                                                                                     |
| **Summary**    | Auto-delete job data and output files after configurable expiry                        |
| **Depends on** | 4.1 (job model with timestamps), 1.3 (`settings.job_ttl_hours`)                       |
| **Blocks**     | None (operational concern, does not block features)                                    |

---

## 1. Objective

Prevent disk exhaustion on a long-running server by automatically cleaning up expired jobs. Each job has a TTL (`settings.job_ttl_hours`, default 24h). After expiry, the cleanup process deletes:

- The job record from the in-memory store.
- The uploaded video file (`storage/uploads/{job_id}.ext`).
- The output directory and all its contents (`storage/outputs/{job_id}/`).

---

## 2. Acceptance Criteria

| #    | Criteria                                                                                               |
| ---- | ------------------------------------------------------------------------------------------------------ |
| AC-1 | A background cleanup task runs periodically (configurable interval, default every 30 minutes).          |
| AC-2 | Jobs in terminal states (`completed`, `failed`, `cancelled`) older than `job_ttl_hours` are deleted.    |
| AC-3 | Jobs still `processing` are never deleted, regardless of age.                                          |
| AC-4 | `queued` jobs older than TTL are deleted (assumed stuck/orphaned).                                      |
| AC-5 | Uploaded video file for expired jobs is deleted from `storage/uploads/`.                                |
| AC-6 | Output directory for expired jobs is deleted recursively from `storage/outputs/`.                       |
| AC-7 | Cleanup failures for individual jobs are logged but do not stop cleanup of other jobs.                  |
| AC-8 | Cleanup task starts automatically when the FastAPI app starts.                                          |

### 3.2 Cleanup Service — `app/services/cleanup.py`

```python
import shutil
import logging
from datetime import datetime, timezone, timedelta
from pathlib import Path

from app.config import settings
from app.models.job import JobStatus, is_terminal
from app.models.job_store import job_store

logger = logging.getLogger(__name__)


def cleanup_expired_jobs() -> int:
    """Delete jobs that have exceeded their TTL.

    Deletes:
    - The job record from the in-memory store.
    - The uploaded video file.
    - The output directory and all contents.

    Returns:
        Number of jobs cleaned up.
    """
    ttl = timedelta(hours=settings.job_ttl_hours)
    now = datetime.now(timezone.utc)
    cutoff = now - ttl

    all_jobs = job_store.list_all()
    cleaned = 0

    for job in all_jobs:
        # Never clean up jobs still processing
        if job.status == JobStatus.PROCESSING:
            continue

        # Clean up terminal jobs past TTL
        # Also clean up queued jobs past TTL (assumed stuck/orphaned)
        if job.updated_at < cutoff:
            try:
                _delete_job_files(job.job_id, job.video_path)
                job_store.delete(job.job_id)
                cleaned += 1
                logger.info(
                    "Cleaned up expired job %s (status=%s, age=%s)",
                    job.job_id, job.status.value, now - job.updated_at,
                )
            except Exception:
                logger.exception(
                    "Failed to clean up job %s — will retry next cycle",
                    job.job_id,
                )

    if cleaned > 0:
        logger.info("Cleanup cycle complete: %d jobs removed", cleaned)

    return cleaned


def _delete_job_files(job_id: str, video_path: str):
    """Delete all files associated with a job.

    Errors are logged but not raised — partial cleanup is acceptable.
    The next cleanup cycle will retry any remaining files.
    """
    # Delete uploaded video
    try:
        upload_path = Path(video_path)
        if upload_path.exists():
            upload_path.unlink()
            logger.debug("Deleted upload: %s", upload_path)
    except OSError:
        logger.warning("Failed to delete upload: %s", video_path)

    # Delete output directory (segments + detection_times.txt)
    try:
        output_dir = Path(settings.output_dir) / job_id
        if output_dir.exists():
            shutil.rmtree(output_dir)
            logger.debug("Deleted output dir: %s", output_dir)
    except OSError:
        logger.warning("Failed to delete output dir for job %s", job_id)
```

### 3.3 Periodic Scheduler — `app/services/scheduler.py`

A lightweight background loop using `asyncio`. No external dependencies (no APScheduler, no Celery Beat).

```python
import asyncio
import logging

from app.config import settings
from app.services.cleanup import cleanup_expired_jobs

logger = logging.getLogger(__name__)

_cleanup_task: asyncio.Task = None


async def _cleanup_loop():
    """Run cleanup_expired_jobs() on a fixed interval."""
    interval = settings.cleanup_interval_minutes * 60  # convert to seconds
    logger.info(
        "Cleanup scheduler started — interval=%dm, TTL=%dh",
        settings.cleanup_interval_minutes, settings.job_ttl_hours,
    )

    while True:
        await asyncio.sleep(interval)
        try:
            cleaned = cleanup_expired_jobs()
            if cleaned > 0:
                logger.info("Scheduled cleanup removed %d jobs", cleaned)
        except Exception:
            logger.exception("Cleanup cycle failed — will retry next interval")


def start_cleanup_scheduler():
    """Start the background cleanup loop. Call once at app startup."""
    global _cleanup_task
    if _cleanup_task is None or _cleanup_task.done():
        _cleanup_task = asyncio.create_task(_cleanup_loop())
        logger.info("Cleanup scheduler task created")


def stop_cleanup_scheduler():
    """Stop the background cleanup loop. Call at app shutdown."""
    global _cleanup_task
    if _cleanup_task and not _cleanup_task.done():
        _cleanup_task.cancel()
        logger.info("Cleanup scheduler task cancelled")
```

### 3.4 Wire Into App Lifecycle — `app/main.py`

Add startup/shutdown events to register the cleanup scheduler:

```python
from contextlib import asynccontextmanager
from fastapi import FastAPI
from fastapi.middleware.cors import CORSMiddleware
from app.config import settings
from app.routers import health, jobs
from app.services.scheduler import start_cleanup_scheduler, stop_cleanup_scheduler


@asynccontextmanager
async def lifespan(app: FastAPI):
    # Startup
    start_cleanup_scheduler()
    yield
    # Shutdown
    stop_cleanup_scheduler()


app = FastAPI(
    title="JBI Detection & Segmentation API",
    version="1.0.0",
    description="API for detecting and segmenting JBI overlays in news broadcast videos.",
    lifespan=lifespan,
)

# CORS middleware
app.add_middleware(
    CORSMiddleware,
    allow_origins=settings.cors_origins_list,
    allow_credentials=True,
    allow_methods=["*"],
    allow_headers=["*"],
)

app.include_router(health.router, prefix=settings.api_v1_prefix, tags=["health"])
app.include_router(jobs.router, prefix=settings.api_v1_prefix, tags=["jobs"])


@app.get("/")
async def root():
    return {"message": "JBI Detection & Segmentation API"}
```

**Changes from Story 1.3:**
- Added `lifespan` context manager using FastAPI's recommended pattern.
- Cleanup scheduler starts on startup, stops on shutdown.

## 4. Cleanup Decision Matrix

| Job Status     | Age > TTL? | Action                  | Rationale                              |
| -------------- | ---------- | ----------------------- | -------------------------------------- |
| `queued`       | No         | Keep                    | Waiting to be picked up                |
| `queued`       | Yes        | **Delete**              | Stuck/orphaned — worker never claimed  |
| `processing`   | No         | Keep                    | Actively running                       |
| `processing`   | Yes        | **Keep**                | May be a very long video; don't kill   |
| `completed`    | No         | Keep                    | User may still download results        |
| `completed`    | Yes        | **Delete**              | Past retention window                  |
| `failed`       | No         | Keep                    | User may want to check error           |
| `failed`       | Yes        | **Delete**              | No longer useful                       |
| `cancelled`    | No         | Keep                    | Recently cancelled                     |
| `cancelled`    | Yes        | **Delete**              | No longer useful                       |

## 5. What Gets Deleted

```
Expired job "abc-123":

  storage/uploads/abc-123.mp4          ← deleted (uploaded video)
  storage/outputs/abc-123/             ← deleted recursively
    ├── segment_000000.mp4
    ├── segment_000001.mp4
    └── detection_times.txt
  In-memory job record                 ← removed from job_store
```

After cleanup, `GET /api/v1/jobs/abc-123` returns `404 Not Found`.

## 7. Design Decisions

| Decision                                        | Rationale                                                                                          |
| ----------------------------------------------- | -------------------------------------------------------------------------------------------------- |
| **`asyncio.create_task` loop, not APScheduler** | Zero new dependencies. FastAPI's event loop is already running — we just add a sleeping coroutine. |
| **Never delete `processing` jobs**              | A 2-hour video might legitimately process for 30+ minutes. Killing it based on wall clock time would be wrong. The TTL applies after the job reaches a terminal state. |
| **Delete stuck `queued` jobs past TTL**          | If a job stays `queued` for 24h, the worker never picked it up. Something is broken — clean up and let the user retry. |
| **`shutil.rmtree` for output dirs**             | Recursively deletes all segment files + detection_times.txt in one call. |
| **Individual job errors don't stop the cycle**   | If one file is locked, the others still get cleaned. The failing job will be retried next cycle. |
| **30-minute default interval**                   | Frequent enough to keep disk usage in check, infrequent enough to not add overhead. Configurable via `CLEANUP_INTERVAL_MINUTES`. |

---

## 8. Notes

- **Clock comparison uses `updated_at`**, not `created_at`. A job completed 1 hour ago (even if created 25 hours ago) is still within the 24h TTL. This gives users the full TTL window from when results became available.
- **Race condition with downloads:** If a user is downloading a segment file at the exact moment cleanup runs, the download will fail mid-stream. This is an acceptable edge case for v1 — clients can retry. A production fix would use reference counting or download tokens.
- **`processing` jobs with `JOB_TTL_HOURS=0`** are still protected. The only way to clean up a stuck processing job is to cancel it first (Story 4.6), then let TTL handle it.
- **Disk usage monitoring** can be added to the health endpoint (Story 6.3) to alert when storage is filling up faster than cleanup can handle.
